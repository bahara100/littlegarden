# 니케 팬 놀이터 구현 계획

작성일: 2026-10-15 (Asia/Seoul)

## 1. 목표와 전제

웹사이트에서 닉네임을 입력하고 입장하면, 2등신 캐릭터를 조종하며 다른 사용자와 같은 놀이터에서 움직이고 기구와 상호작용한다.

- 1차 목표: PC 브라우저에서 2명 이상이 같은 방에 접속해 이동·그네 탑승·고유 모션을 서로 확인한다.
- 공개 베타 목표: 방당 최대 16명. 수용 인원은 실기기·부하 테스트 결과에 따라 조정한다.
- 시점: 위에서 약간 내려다보는 2D. 캐릭터 발 위치를 기준으로 앞뒤 가림을 처리한다.
- 운영: 클라이언트는 GitHub Pages, 실시간 서버는 별도 Node.js 호스팅.
- 초기에는 게스트 세션만 제공하며 회원가입·영구 저장은 도입하지 않는다.
- 니케 IP의 게임 제작·배포 허용 여부는 아직 확인되지 않았다. 임시 자체 캐릭터로 기술 검증을 진행하고, 니케 캐릭터를 활용한 제작·공개 범위는 공식 가이드라인 또는 권리자의 답변으로 확인한다.

## 2. 첫 버전 범위

| 항목 | 구현 사양 |
| --- | --- |
| 입장 | 닉네임 2~12자, 앞뒤 공백 제거, 제어문자 제외, 일반 텍스트로 표시 |
| 사용자 식별 | 닉네임과 별도 세션 ID 사용. 동명은 허용하며 본인에게 표시 강조 |
| 캐릭터 | 1종. 대기·4방향 걷기·앉기·손 흔들기 또는 고유 모션 1개 |
| 맵 | 논리 좌표 1600×1000의 놀이터 1개를 초안으로 제작 |
| 이동 | WASD/방향키. 대각선 속도 보정, 맵 경계·장애물 충돌 |
| 상호작용 | 근처에서 E 또는 화면 버튼. ESC/하차 버튼으로 종료 |
| 벤치 | 좌석 2개. 좌석별 한 명 탑승 |
| 그네 | 좌석 1개. 정해진 주기의 연출 애니메이션 |
| 모션 | 숫자키 1 또는 화면 버튼. 기본 2초, 재사용 대기 3초를 초안으로 적용 |
| 방 | 첫 빈 방에 자동 입장. 가득 차면 새 방 생성. 방 코드 표시·입력으로 지인과 합류 |
| 연결 UI | 접속 중·접속 실패·재연결 중·방 가득 참·버전 불일치 표시 |
| 재접속 | 15초 이내 세션 복귀 시도. 끊긴 사용자의 좌석은 즉시 해제하고 복귀 시 가까운 안전 지점에 배치 |

첫 버전 제외: 채팅, 음성, 계정, 재화, 결제, 인벤토리, 캐릭터 간 밀치기, 사용자 제작 콘텐츠, 실제 그네 물리, 두 사람이 동기화하는 시소.

## 3. 사용자 흐름

1. 접속 → 리소스 로딩 및 진행 표시.
2. 닉네임 입력 → 자동 입장 또는 방 코드로 입장.
3. 서버가 세션과 초기 상태 발급 → 안전한 시작 지점에 등장.
4. 짧은 조작 안내 → 이동·기구 사용·모션 실행.
5. 퇴장 또는 연결 끊김 → 서버가 사용자와 점유 자원 정리.

플레이 중 화면에는 본인 캐릭터, 다른 사용자 닉네임, 방 코드/인원, 모션 버튼, 가까운 기구의 사용 안내, 연결 상태를 표시한다. 모바일은 별도 단계에서 가상 조이스틱과 큰 터치 버튼을 추가한다.

## 4. 기술 구성

- 클라이언트: Phaser + TypeScript + Vite. 입장·오류 화면은 HTML/CSS로 구현.
- 서버: Node.js + TypeScript + Colyseus. 서버가 이동과 상호작용을 확정.
- 공통 모듈: 메시지 타입, 이동 규칙, 충돌 정보, 맵/기구 정의, 프로토콜 버전.
- 패키지 관리: npm workspaces. 구현 시작 시 호환되는 안정 버전을 선택하고 lockfile로 고정.
- 자동 검사: 타입 검사, 빌드, 서버 규칙에 대한 핵심 테스트.
- 배포: GitHub Actions로 클라이언트 빌드 후 GitHub Pages에 게시. 서버는 별도 배포.

```text
apps/
  client/                 # 입장 UI, Phaser 장면, 입력, 네트워크, 표시
    public/assets/        # 캐릭터·맵·기구 이미지와 메타데이터
  server/                 # 방, 이동 검증, 좌석 관리, 연결 생명주기
packages/
  shared/                 # 타입, 이동/충돌 규칙, 맵 및 기구 정의
.github/workflows/        # 검사 및 Pages 배포
docs/                     # 에셋 규격, 배포 절차, 운영 기록
```

## 5. 실시간 처리

### 이동

- 클라이언트는 위치를 확정해서 보내지 않고, 이동 방향과 입력 순번을 전송한다.
- 서버는 고정 간격으로 속도·경계·충돌을 계산한다.
- 초기 설정은 서버 계산과 상태 전송을 초당 20회로 두고 측정 후 조정한다.
- 입력에는 순번과 지속 시간을 사용하고 서버가 허용 범위를 제한한다. 입력이 일정 시간 없으면 정지시켜 연결 끊김으로 계속 이동하지 않게 한다.
- 본인은 로컬 예측과 서버 보정, 타인은 최근 상태 보간으로 부드럽게 표시한다.
- 클라이언트와 서버는 같은 이동/충돌 규칙을 사용한다.
- 플레이어 간 충돌은 적용하지 않아 길막과 동기화 복잡도를 줄인다.

### 공유 상태

- Player: 세션 ID, 닉네임, 캐릭터 ID, x/y, 방향, 행동, 행동 시작 시각, 기구/좌석 ID, 마지막 처리 입력 순번.
- Equipment: 기구 ID, 좌석별 점유자, 동작 시작 시각, 동작 상태.
- Room: 방 코드, 맵 버전, 정원, 사용자/기구 목록, 프로토콜 버전.
- 닉네임 외 개인정보는 수집하지 않으며 재접속 토큰은 공개 방 상태에 포함하지 않는다.

### 기구와 모션

- 이동 가능 상태: idle / walk. 제자리 동작: emote. 탑승 상태: seated / swinging.
- 탑승 중에는 이동 입력을 무시하고 하차만 허용한다. emote 중 이동하면 모션을 취소한다.
- 서버는 거리·현재 행동·좌석 유무를 검증한 뒤 좌석을 원자적으로 할당한다. 같은 좌석 동시 요청은 하나만 성공한다.
- 그네는 기구의 공통 시간축에서 각도와 좌석 위치를 계산한다. 사용자별로 시작 시점을 새로 잡지 않는다.
- 캐릭터는 그네 좌석 앵커를 따라 움직인다. 그네 프레임·줄·좌석·캐릭터의 표시 순서를 분리한다.
- 하차는 기구 앞 안전 지점을 확인해 배치하며, 막혀 있으면 대체 지점을 사용한다.
- 퇴장·연결 끊김·방 정리 때 좌석 점유를 해제한다.
- 모션은 ID와 서버 시작 시각을 공유하고 각 브라우저가 이미지 프레임을 재생한다.

## 6. 아트 제작 규격 초안

- 캐릭터 프레임: 128×128px 투명 PNG. 발 기준 앵커와 프레임 크기 통일.
- 전신 비율: 약 2등신. 표시 크기는 맵과 첫 시안을 보고 결정.
- 대기: 4방향 × 4프레임, 걷기: 4방향 × 6프레임.
- 앉기/그네 자세: 화면을 향하는 지정 방향 × 4프레임. 초기 기구 방향을 이에 맞춰 통일.
- 고유 모션: 정면 × 8프레임. 1차 초안 총 52프레임이며 최종 수량은 시안 검수 후 확정.
- 좌우 반전은 캐릭터의 비대칭 의상·장식에 문제가 없는 경우에만 사용.
- 메타데이터에 프레임 범위·속도·반복 여부·발 앵커·좌석 오프셋을 기록.
- 캐릭터 추가는 이미지와 설정 등록으로 가능하게 만들고 게임 규칙과 분리.
- 배경은 바닥, 충돌물, 전경을 나눠 작성. 그네는 프레임과 움직이는 부품을 분리.
- 제작 순서: 임시 캐릭터로 기능 검증 → 치비 1종의 정면/후면/측면 시안 → 걷기 → 앉기 → 고유 모션 → 추가 캐릭터.
- 원작 리소스 추출을 전제로 삼지 않는다. 사용 에셋별 제작자·출처·사용 허용 범위를 기록.

## 7. 단계와 완료 기준

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 0. 범위 확정 | 임시 캐릭터, 맵 배치, 조작, 에셋 규격 | 기술 검증용 자체 에셋과 맵 정의 준비 |
| 1. 기본 화면 | 작업 공간, 입장 UI, 로컬 맵/이동/충돌 | 브라우저에서 입장하고 벽을 통과하지 않고 이동 |
| 2. 멀티플레이 | 방, 세션, 서버 이동, 보간/예측, 방 코드 | 서로 다른 브라우저 2개에서 이동·입퇴장 확인 |
| 3. 상호작용 | 벤치, 그네, 고유 모션, 좌석 정리 | 두 사용자가 같은 기구 상태와 모션을 확인; 동시 탑승 경쟁 정상 처리 |
| 4. 아트 적용 | 허용 범위 확인된 캐릭터/배경, 가림 순서 | 캐릭터 발·좌석 정렬, 앞뒤 가림, 프레임 연결 검수 |
| 5. 배포 | Pages, 별도 서버, HTTPS/WSS, 환경 설정 | 다른 네트워크의 PC 두 대가 공개 주소에서 함께 플레이 |
| 6. 공개 베타 준비 | 지연/부하/장시간/재접속 검증 | 16명 목표 검증, 연결 오류 안내, 운영 절차 작성 |
| 7. 확장 | 모바일 터치, 캐릭터 추가, 추가 기구 | 모바일 실기기에서 터치로 주요 기능 조작 |

첫 검토 시점은 3단계 완료 후다. 이때 실제 치비 아트 제작 범위를 확정한다. 4단계 아트 제작은 2~3단계 기술 작업과 일부 병행할 수 있다.

## 8. 검사 항목

- 핵심 자동 테스트: 대각선 속도, 경계/충돌, 입력 검증, 거리 밖 탑승 거부, 좌석 동시 점유 방지, 모션 중 이동, 하차 위치, 접속 종료 시 좌석 반환.
- 수동 확인: 두 브라우저 및 두 네트워크 접속, 같은 방 합류, 모션 동시 표시, 탑승 중 새 사용자 입장, 재연결, 서버 재시작, 탭 비활성화 후 복귀.
- 지연 조건: 왕복 지연 100~200ms 환경에서 이동 끊김과 위치 보정 정도 관찰. 모바일 전환 시 네트워크 변동도 확인.
- 부하 목표: 16개 클라이언트로 30분 이동/상호작용. 서버 틱 시간, CPU, 메모리, 송수신량, 오류 및 좌석 누수 기록.
- 렌더링 목표: 합의한 기준 PC에서 60fps를 지향하되 아트 적용 후 측정. 모바일 목표는 기기 선정 후 정한다.
- 배포 확인: Pages의 저장소 하위 경로에서 에셋 로딩, HTTPS 페이지에서 WSS 연결, 서버 장애 시 안내, 클라이언트/서버 버전 불일치 처리.

## 9. 배포와 운영

- GitHub 저장소 한 곳에서 전체 소스 관리. Pages에는 클라이언트 빌드 결과만 배포.
- Vite base와 에셋 경로를 저장소 하위 경로에 맞춘다.
- 공개 서버 주소는 클라이언트 빌드 환경 변수로 설정한다. 이는 공개 정보이며 비밀키를 포함하지 않는다.
- 서버는 WebSocket 업그레이드, TLS, 상시 실행 여부, 지역, 메모리, 트래픽, 무료 한도와 절전 조건을 기준으로 선정.
- 서버는 컨테이너 또는 일반 Node.js 실행으로 옮길 수 있게 구성한다. 제공 업체와 실제 비용은 배포 단계에서 당시 조건으로 확인.
- 개발/테스트 서버와 공개 서버 설정 분리. 빌드에 프로토콜 버전을 넣고 호환되지 않으면 새로고침 안내.
- 서버 배포 중 방은 초기화될 수 있음을 UI에 안내. 첫 버전은 위치와 세션을 디스크에 저장하지 않는다.
- 기본 운영 장치: 메시지 형식/크기 검증, 빈도 제한, 허용 캐릭터/기구 ID 검사, 방 정원/방 수 상한, 유휴 사용자 정리, 상태 확인 엔드포인트, 오류 로그.
- Origin 제한은 보조 장치로만 사용하고 서버 검증을 대체하지 않는다. 악성 접속에 대한 IP별 제한은 프록시 설정을 확인해 적용한다.
- 공개 전 닉네임 신고/세션 퇴장 등 최소 관리 절차를 정한다. 채팅은 관리 기능 마련 후 검토한다.
